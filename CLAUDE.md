# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What it is

NymPlayer is a Rust desktop app, released for Windows only (it builds on macOS and Linux, see Platform code), that passes live audio from an input device (typically a USB audio interface) to a chosen output device (speakers, Bluetooth headphones). The GUI has input/output dropdowns, level meters, volume/mute, and Play/Stop. User-facing description: `readme.md`.

## Commands

```sh
cargo build --release          # binary: target/release/nymplayer.exe
cargo build --profile dist     # as published: + LTO, deps optimized for size (rubato at -O3): 7.7 MB vs 13 MB
cargo test                     # unit tests (converter, settings parsing, meter scale)
cargo test resamples_48k       # run a single test by name filter
cargo fmt                      # format (rustfmt.toml: 120 columns)
cargo clippy --all-targets     # lint; keep it warning-free
python assets/make_icon.py     # regenerate assets/icon.png + icon.ico (stdlib only)
```

The release build fails with "failed to remove file ... nymplayer.exe" when the app is running; close it first.

## Architecture

App code is in `src/main.rs`. Platform code lives under `src/system/` (see Platform code). On Windows (`src/system/windows.rs`):
- **Single instance:** a named event `Local\NymPlayer.Show`. A second copy signals it and exits; the first copy's waiting thread turns the signal into `Cmd::Show`.
- **PC sound:** `PcSound` (process loopback), see below.
- **Autostart:** the `HKCU\...\Run` value `NymPlayer`, which launches the exe with `--tray`. The registry is the source of truth for the checkbox.

`build.rs` embeds `assets/icon.ico` into the exe via `winresource`. `assets/icon.png` is used as the window icon and is generated by `make_icon.py`, so edit the script, not the PNGs.

Audio path, in `start()`:
- **cpal (WASAPI)**: an input stream and an output stream, each with its own callback thread.
- **Input callback** (`build_input::<T>`, generic over f32/i16/i32/u16) converts to f32 and pushes into a `ringbuf` lock-free SPSC buffer (capacity 5× target). It pushes **whole frames only**, so channels never get shifted. When the buffer is full, the newest audio is dropped (a safety net only).
- **Output callback** runs `Converter::fill`:
  - It waits until `TARGET_MS` (40 ms) is buffered, and waits again after each underrun. When it (re)starts, it discards any backlog beyond the target, since the drift correction would only drain it slowly.
  - It resamples with rubato's `Async` sinc resampler (fixed output chunks of `CHUNK` frames, ratio = out_rate / in_rate). Resampled frames sit in `pending[pos..]` until they're played.
  - **Drift correction:** each callback nudges the ratio (±0.5% max, via `set_resample_ratio_relative`) in proportion to how far the smoothed buffer fill is from the target. This keeps the latency steady when the two device clocks differ, instead of dropping audio or underrunning.
  - It maps channels: extra output channels repeat the last input channel, so mono feeds both ears.
  - Output buffers arrive pre-filled with silence from cpal.
- After the converter, the output callback multiplies by the gain (`App::gain`, f32 bits in an `AtomicU32`; 0 when muted).
- The audio callbacks must not allocate: the scratch buffers are sized up front.
- `Shared` (atomics only) carries peak levels (f32 bits with `fetch_max`) and a `failed` flag set by the cpal error callbacks (`fail()`). Non-fatal errors (`Xrun`, `DeviceChanged`, `RealtimeDenied`) don't set it: the stream keeps running, and a restart is more audible than the glitch.
- Diagnostics: run with `NYMPLAYER_TRACE=<file>` and `App::trace` appends one line per second (unix time, buffer fill in ms, underruns, dropped input frames, xruns, failed, status), from counters in `Shared`. Counters reset when the streams restart.

Casting (`src/cast.rs`, experimental), an alternative to the local output device (`enum Output` in `start()`):
- **Discovery:** `cast::Discovery::search` sends one mDNS question (`QUERY`: PTR `_googlecast._tcp.local`) from a random port ("legacy unicast"), three times over 4 s, and `parse_reply` reads the replies' SRV/TXT/A records (`dns_name` follows compression pointers). The socket is bound to the adapter with the default route (`query_socket`), because Windows otherwise sends multicast out of a virtual adapter (Hyper-V, VPN). Windows Firewall lets unicast replies to a multicast question in for a few seconds, which is why it asks repeatedly. Devices are unique by name, not IP: a speaker group is announced at one of its speakers' IPs (on another port).
- **Session:** `cast::Session::start` serves the live input as endless 16-bit stereo WAV over a small `std` HTTP server (bound to the local address that routes to the speaker), then a control thread (`control`/`run`) speaks the Cast v2 protocol itself (`Channel`): TLS via `rustls` (ring only; speakers' self-signed certificates are accepted, handshake signatures checked: `SelfSigned`), 4-byte length + protobuf `CastMessage` (`cast_message`/`read_cast_message`, fields 1–6) carrying JSON. It connects, LAUNCHes the Default Media Receiver (`CC1AD845`), reads its transport/session ID from RECEIVER_STATUS (`media_app`), LOADs the URL as a LIVE stream, answers heartbeat PINGs and sends its own every 5 s; `ended_by` maps MEDIA_STATUS idle reasons, LOAD_FAILED, CLOSE and a RECEIVER_STATUS without our session to a reason. JSON is read with `json_str` (compact JSON, unescaped values only), so no JSON library. The ring buffer holds 2 s for casting. Only requests for the session's random secret path are served (`secret()`, the std hasher's random keys), so other LAN devices can't listen or take over; a new valid request takes over and clears stale audio. Writes time out after 5 s, so a stalled speaker can't block the thread.
- **Threads:** all blocking code: one thread per discovery, two per session (HTTP stream, Cast control with 100 ms read timeouts so Stop is noticed). No async runtime: `oxicast` + `tokio` were replaced by this (−1.2 MB together with dropping `mdns-sd`; `rustls`'s default would also have added `aws-lc`).
- **Ending:** dropping `Session` stops the stream and the speaker app. If the speaker ends the session, or never fetches the stream within 10 s (usually the firewall), `Session::ended` returns a reason; `sync()` then stops playback rather than switching to the local output.
- The speaker must open an incoming connection to this PC, so a firewall that blocks inbound traffic (e.g. company policy) makes casting impossible. Live WAV casting is confirmed working on a real Google speaker (a few seconds of buffering, set by the receiver); the streaming is also covered by the loopback test `serves_live_wav_over_http`.

Device handling, in `App::sync()`:
- `sync()` runs every second from `App::logic()`, which (unlike `ui()`) still runs while the window is minimized. It also runs on any device or Play/Stop change.
- It re-enumerates devices and decides which devices to use: the saved selection if it's present, otherwise the Windows default. An empty selection string means "follow the Windows default".
- It restarts the streams when that decision changes or when `failed` is set. This is how unplugging, re-plugging and default-device changes are handled.
- Dropping `Running` stops the streams.

Recording (`src/record.rs`, issue #1), the third kind of output (`Output::Record`): only the file, no playback or casting:
- `record::Recording::start` creates the file up front (a bad folder fails immediately), then a writer thread drains the ring buffer (2 s) every 20 ms. The audio callback never touches the disk. The input is written **untouched**: no gain or mute, per the issue.
- Formats: 16-bit WAV via `hound`; 16-bit FLAC via `flacenc`, encoded **frame by frame** (`encode_fixed_size_frame`, 4096-frame blocks) so memory stays flat. The STREAMINFO header is written first and rewritten with the final counts on finish. The short last block is padded to FLAC's 32-frame minimum.
- Input gaps over `record::GAP` (100 ms) are recorded as silence, since loopback sends nothing while the PC is quiet.
- Dropping `Recording` stops it, drains the buffer and finishes the file (joins the thread). A write error also finishes the file; `ended()` gives the reason for the status line.
- `sync()` never restarts a running recording: if the input changes or fails, it ends the recording (keeping the file) instead, since a restart would overwrite it. `App::recording` (`record::Target`: path + format) takes precedence over casting and the local output; when it's cleared, the previous playback state resumes.
- The save dialog (`rfd`) runs on **its own thread** (`open_save_dialog`); `logic` picks up the answer from `save_dialog`. On Windows, cpal initialises the GUI thread's COM as multithreaded, and the file dialog (single-threaded COM) then fails silently. The file name uses `system::local_timestamp()`.
- Tests: WAV and FLAC round trips through the real writer thread (FLAC decoded with flacenc's `decode` feature, a dev-dependency), silence during gaps, and a bad folder.

PC sound input (`system::PcSound`, Windows only for now; `system::PC_SOUND` is its label, `None` elsewhere):
- "All PC sound (except NymPlayer)" (ID `PC_SOUND_ID`) captures every other program's sound with **process loopback** (`wasapi` crate, `new_application_loopback_client` in exclude mode with NymPlayer's own PID), on its own MTA thread, as 48 kHz float stereo (`PC_SOUND_RATE`, Windows converts).
- Why not plain WASAPI loopback of an output device (cpal's "input on an output device")? It captures *after* the endpoint volume and the driver's effects. Measured on a Realtek laptop with Dolby: about 29 dB too quiet at 14 % volume and about 20 dB bass-heavy. Process loopback is a clean digital copy (flat within 0.1 dB at any volume). Don't go back to it.
- NymPlayer's own output is never captured, so there's no echo when it plays the PC sound back through the same speakers; no feedback guard is needed.
- `Input::PcSound` sits next to `Input::Device` in `sync()`/`start()`; `push_input()` is shared with the cpal input callback. Settings saved with the old `loopback:<id>` inputs migrate to `PC_SOUND_ID` in `Settings::parse`.
- It sends nothing while nothing plays, so casting (`cast::GAP`) and recording (`record::GAP`) fill gaps with silence.
- Needs Windows 10 build 20348 or later; on older versions starting it fails with an error in the status line.

Device identity:
- Devices are identified by **cpal's `DeviceId`**, kept as a string (`dev_id()`, e.g. `wasapi:{0.0.0.00000000}.{guid}`). Settings store the ID; an empty string means "Windows default".
- The dropdowns show `Entry::label`, the device name with duplicates numbered "(2)", "(3)".
- `migrate()` converts settings saved before IDs existed, which hold a device name: once a device with that name is present, the setting is switched to its ID and saved.
- Get names via `description().name()`. Never use `Device::to_string()`: its `Display` impl returns `fmt::Error` for a vanished device, and that panics.

Tray and window:
- The tray icon (`tray-icon` crate) uses the exe's embedded icon (resource 1).
- Tray mode is tied to autostart (`App::autostart`). When it's off, the icon is hidden (`show_tray_icon`), minimize behaves normally, and `--tray` is ignored. The `Tray` is still created, because its channel also carries Show requests from a second copy of the app.
- Tray and menu events arrive in handlers outside egui. Those handlers send a `Cmd` over an mpsc channel and call `request_repaint`, and `App::logic` drains the channel. This also works while the window is hidden.
- When the window reports it's minimized, `logic` hides it (`Visible(false)`).
- eframe always makes the window visible after its first frame, so `ViewportBuilder::with_visible(false)` doesn't work. `--tray` instead minimizes the window at startup, and the minimize-to-tray logic then hides it.
- `src/system/windows.rs` has a registry test, `autostart_round_trip`. It's `#[ignore]`d because it touches the real Run key (and restores it); run it with `cargo test -- --include-ignored`.

Settings (`Settings`) are lines in `NymPlayer/settings.txt` under `system::config_dir()` (`%APPDATA%` on Windows): input device ID, output device ID, volume, muted (0/1), playing (0/1), last recording folder, last recording format (file extension). Playback resumes at startup if `playing` was set. Missing lines fall back to defaults, so older two-line files still load. They're saved on change; for the volume slider, only when a drag ends.

GUI notes:
- eframe/egui 0.36 uses `App::ui(&mut self, ui, frame)`, not `update`.
- Start-up speed: eframe uses the **glow** (OpenGL) renderer with default features off. The default wgpu renderer took 1.9–3 s to start on Windows, while glow takes about 0.2 s. Don't re-enable wgpu or eframe's default features without measuring. Opening the audio streams takes about 250 ms, so `App::new` only lists devices, and the first `sync()` (which resumes playback) runs on the first `logic` pass after the first frame is drawn.
- The theme lives in `apply_theme`; its colours (`ACCENT`, `WOOD`, …) are taken from the icon.
- The slider rail uses `widgets.inactive.bg_fill`, so that colour must differ from the `SURFACE` panel the slider sits on.
- egui's built-in fonts lack many Unicode symbols (`→`, `●` render as boxes). Paint shapes with the painter or use plain text instead.

## Platform code

All OS-specific code lives under `src/system/`. `src/system.rs` picks `windows.rs` or `other.rs` (macOS/Linux fallbacks: no single instance, autostart or tray icon) and its doc comment lists the API every platform file provides. `main.rs` only calls `system::*` and must stay platform-neutral (its `#![windows_subsystem]` attribute is the one exception; other targets ignore it). The release workflow (`v*` tags) builds and tests on Windows, macOS (arm64) and Linux (Ubuntu 22.04), and publishes all three. Releases fail if any platform fails, so run CI (manual only: Actions tab, "Run workflow") before tagging when platform code changed.

**Warn the user whenever a change would put OS-specific code outside `src/system/`**, then move it behind the `system` API instead. Signs of creep:
- `#[cfg(windows)]`, `cfg!(target_os = ...)`, `windows-sys`/Win32 calls, or Windows-only crate APIs such as `Icon::from_resource`
- Windows paths or environment variables (`%APPDATA%`, the registry, `\` separators in code)
- user-facing text that names Windows ("Windows default", "Start with Windows"); take it from a `system::` constant
- new dependencies that only build on one OS: declare them under `[target.'cfg(...)'.dependencies]` in Cargo.toml
